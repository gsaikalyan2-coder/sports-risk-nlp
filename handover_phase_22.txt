PART A — PROJECT SUMMARY
--------------------------------------------------------------------------------

Pre-Competition Psychological Risk Profiling of Athletes. NLP x sports
psychology: detect 10 validated constructs (CSAI-2 / SDT / ABQ tradition) in
athlete text and fuse them into an interpretable risk index with two-level
explanations (span->construct, construct->risk). Owner: Saikalyan, sophomore at
SRMIST. Target: IEEE conference (iTriply Explore), full paper, draft due first
week of September 2026. Python 3.11. Repo: C:\Users\x\sports-risk-nlp.

Phases 1-15 and 17-22 are complete. Phase 16 (DataRobot AutoML) was skipped by
decision. **Phase 22 is complete and its gate PASSED.** Next is Phase 23, IEEE
draft assembly.

THE CONSTRAINT THAT GOVERNS EVERYTHING — carry it forward verbatim.

data/gold/ is empty. **No number in this repository is an accuracy.** Every
result is a corpus property of a synthetic template grammar (synth_precomp_v1,
4,000 generated records, labels planted by the generator). Never report a figure
as accuracy. Never write to data/gold/. Never weaken the --gold refusal in
src/models/dataset.py. An attribution is a claim about the model, not about
athlete psychology.

Six corollaries, all binding:

  Phase 18: a gate that only checks a result *exists* is worse than no gate,
            because it launders the claim.
  Phase 19: the claim ledger is upstream of the prose. Any headline sentence not
            traceable to a row in src/evaluation/ablations.py::CLAIMS requires a
            new Claim, added and passing the gate, BEFORE it is written anywhere.
  Phase 20: a property the unit tests can see is not the whole property. Two
            defects passed every test and were caught only by rendering the page
            and looking at it.
  Phase 21: a detector that fires on everything is exactly as uninformative as
            one that fires on nothing. A gate needs a proven floor and a legible
            ceiling.
  Phase 22: a claim about an artefact and the STRENGTH of that claim are one
            object. "It reproduces" with the strength left unstated is not a
            finding; and a check performed where it could not have failed is not
            evidence.
  Running through all six: the check and the thing it protects keep turning out
  to be related by ASSUMPTION rather than by CONSTRUCTION. That is the defect
  shape this project has now found six times. Assume it is present in your phase.

B3. HOW THE GATE WAS STRENGTHENED — BEFORE ANYTHING RAN
-------------------------------------------------------
The plan's gate as written ("fresh clone reproduces headline numbers within
tolerance") is answerable by a person sitting in a directory that already
contains everything. Six additions, each mechanical:

  1. AN ARTEFACT CANNOT BE DECLARED WITHOUT ITS STRENGTH. Match.BYTE_IDENTICAL
     forbids a tolerance; WITHIN_TOLERANCE demands a positive one AND its units;
     NOT_REPRODUCIBLE demands a why_not sentence. There is no way to write "it
     reproduces" and leave the strength unstated.
  2. THE TOLERANCE WAS DECLARED BEFORE ANY RE-RUN, AND IS HASHED.
     ReproductionPlan.declaration_sha256() fingerprints the whole plan including
     every tolerance; --declare freezes it in reports/reproduction.json; every
     verification carries the frozen hash and gate() fails if it no longer
     matches. A tolerance widened after the delta is known invalidates the run
     that used it. Claim row: reproduction_tolerance in ablations.py::CLAIMS,
     added and passing the gate before the sentence was written anywhere.
  3. A VERIFICATION IN A CONTAMINATED TREE IS REFUSED. inspect_tree checks the
     directory before measuring and exits 2. This is the defect
     handover_phase_21.txt predicted for this phase, refused mechanically rather
     than remembered.
  4. cannot_reproduce IS MANDATORY PER STEP, copying ScannerResult.does_not_cover.
     A declared artefact carrying no verdict fails the gate, so the run cannot be
     silent about what it skipped.
  5. A pip COMMAND INSTALLING A LOCAL-VERSION LOCK WITHOUT --extra-index-url IS
     UNCONSTRUCTABLE (MissingExtraIndex). torch==2.13.0+cpu exists on no default
     index; a command that only works for a reader who remembers a flag is not a
     one-command path.
  6. EACH STEP DECLARES THE PATHS IT MAY READ; an observed read outside that set
     fails the gate as a hidden input.

C5. PREDICTED DEFECT SHAPE FOR PHASE 23
---------------------------------------
Every handover since 18 has named one. The shape is always the same: THE CHECK
AND THE PROPERTY IT PROTECTS ARE RELATED BY ASSUMPTION RATHER THAN BY
CONSTRUCTION. Here is where it will land in Phase 23.

**The paper will be checked by the tools that check STRINGS, and its claims live
in NUMBERS AND FIGURES.**

Specifically: assert_no_forbidden_language and the CLAIMS ledger both operate on
text. main.tex will pass both while asserting something false, because the
falsehood will live in a place neither tool reads:

  * A NUMBER TRANSCRIBED BY HAND. Every figure in the paper will be typed or
    copy-pasted out of reports/results.json into LaTeX. Nothing checks that
    "0.588" in main.tex is the 0.5877114720181955 in the ledger — the claim gate
    checks that the EVIDENCE exists, never that the PROSE quotes it correctly.
    One transposed digit passes every gate this project has. Phase 22's answer to
    the analogous problem was FILE_DIGESTS and dotted locators; the analogue here
    is a macro file generated from results.json (\newcommand{\macroF}{0.588}) so
    the paper cannot quote a number the ledger does not hold. Build that BEFORE
    writing the results section, not after.
  * A FIGURE THAT DISAGREES WITH ITS CAPTION. The screen reads the caption and
    never the SVG. Phase 20 already found a chart whose hatch silently vanished
    and every test still passed.
  * A CAVEAT THAT TRAVELS SEPARATELY FROM ITS NUMBER. OPEN-021 (the lexicon floor
    is not independent of the corpus) and the four-inert-constructs
    qualification are both attached to figures by CONVENTION. The moment 0.462 or
    "ten constructs" appears in an abstract, an intro and a results table, three
    of the four copies will lose their caveat, and no tool will notice — a
    caveat's binding to its number is exactly the relationship-by-assumption this
    project keeps rediscovering.
  * AND THE ONE MOST LIKELY TO EMBARRASS: the paper will describe a reproduction
    the reader cannot perform, because "we release a reproducible artifact" will
    be written from the artifact's OWN documentation rather than from what tier B
    actually does. If main.tex says the transformer result is reproducible in
    minutes without saying reports/predictions/ is committed, the paper overstates
    exactly where Phase 22 was most careful not to.

Recommended first move: generate paper/generated_numbers.tex from
reports/results.json and reports/reproduction.json, add a Claim row asserting the
paper quotes only generated macros, and make the compile depend on it. Then write
prose.

A22.4  THE POWERSHELL REDIRECT CORRUPTS THE BASELINE  (found 2026-08-24)
------------------------------------------------------------------------
    docker compose run --rm app detect-secrets scan > .secrets.baseline
    -> UnicodeDecodeError: 'utf-8' codec can't decode byte 0xff in position 0

PowerShell's `>` writes **UTF-16LE with a BOM**, and CRLF line endings. The 0xff
is the BOM's first byte. detect-secrets reads UTF-8, so the very command the
Phase 21 handover prescribed for closing SEC-03 destroys the file it is meant to
regenerate. Confirmed on disk: BOM `377 376`, CRLF throughout, 5,120 bytes.

CORRECT FORM — the redirect must happen INSIDE the container, where the shell is
POSIX and the encoding is UTF-8:

    docker compose run --rm app sh -c 'detect-secrets scan > .secrets.baseline'

AND THE SUITE WAS FULLY GREEN WHILE THE FILE WAS CORRUPT. Every baseline test in
tests/test_security.py builds its own file under tmp_path, so they prove the
PARSER works and prove nothing about the artefact that ships. Seventh instance
of the project's defect shape, and the first one found in the test suite's own
coverage rather than in the code it covers.

FIX: two tests that read the real path —
  test_the_committed_baseline_is_utf8_and_parses    (rejects all three BOMs,
      then json.loads the actual committed bytes and requires results +
      generated_at)
  test_every_committed_baseline_path_is_posix       (a Windows-host rescan
      silently reverts Phase 21's POSIX conversion; this catches the revert)

A22.6  THE REGENERATED BASELINE WAS EMPTY — AND EMPTY READ AS CLEAN
--------------------------------------------------------------------
After fixing the UTF-16 corruption (A22.4), the container scan produced a
well-formed, UTF-8, POSIX baseline with `"results": {}` — zero findings over the
entire repository — and `generated_at` freshly stamped. It looked like the
cleanest possible outcome. It was a scan that read no files.

CAUSE. `detect-secrets scan` enumerates the tree via `git ls-files`. Inside the
container the repo arrives as a bind mount owned by the host UID, while the
image runs as `appuser` (UID 1000), so git refuses it for dubious ownership,
`git ls-files` returns nothing, and the scan dutifully finds no secrets in the
zero files it was handed. Nothing in the output says "I scanned 0 files".

The pre-commit hook then blocked the commit with three Hex High Entropy String
findings the empty baseline could not filter:
    src/reproducibility/manifest.py:90  FILE_DIGESTS["corpus_records"]
    src/reproducibility/manifest.py:91  FILE_DIGESTS["utterances"]
    reports/reproduction.json:15        declared_sha256
All three are SHA-256 digests this project publishes ON PURPOSE — two corpus
fingerprints and the claim-ledger digest that makes the Tier-A reproduction
checkable. None is a credential. The hook was right to stop; the baseline was
wrong to be empty.

CORRECT REGENERATION COMMAND (all three fixes, together):
    docker compose run --rm app sh -c 'git config --global --add safe.directory /app && detect-secrets scan > /tmp/baseline.json && cp /tmp/baseline.json .secrets.baseline'
    docker compose run --rm app detect-secrets audit .secrets.baseline

THREE fixes, not two, and the third was learned the hard way. Redirecting
straight onto `.secrets.baseline` TRUNCATES IT THE INSTANT THE COMMAND STARTS,
before the scan has produced anything. The scan is slow over a Docker Desktop
bind mount (realpath on every tracked file crossing the Windows filesystem
boundary), and an owner who interrupts it — reasonably, because it looks hung —
is left with a ZERO-BYTE baseline and no way back except regenerating. Observed

the operation atomic: a failed or interrupted scan leaves the previous baseline
untouched. Apply the same shape to any command that regenerates a committed
artefact.

Rule all three entries NOT a secret. Anything offered that is not a SHA-256

A22.7  THE AUDIT PROMPT'S POLARITY IS INVERTED — AND IT RECREATED PHASE 21's BUG
--------------------------------------------------------------------------------
`detect-secrets audit` asks, for each finding, whether it is a VALID SECRET —
i.e. not a false positive. Answering `y` therefore writes is_secret: true, which
is the opposite of what "yes, I have checked this and it is fine" feels like.

asserting the repository contains seven live secrets.

That is character-for-character Phase 21's first HIGH finding, recreated three
months later by the same tool with the same prompt, on a fresh scan. It is not a
mistake anyone learns their way out of; it is an interface that produces the
wrong answer for the intuitive keypress. The defence has to be a check, not care.

test_no_baseline_entry_is_left_unaudited CAUGHT IT — written an hour earlier for
exactly this, and it fired on the first run after the audit, before the commit.

interactive prompt with confusing polarity, following the Phase 21 precedent.
Each of the seven was re-verified FIRST — exactly one 64-hex SHA-256 on the line,
sitting on a published digest field — and the script REFUSES to flip anything
