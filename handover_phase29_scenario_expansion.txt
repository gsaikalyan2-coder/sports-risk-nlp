   use SYNTHETIC scenario data instead -- no real athlete, no link, no photo,

   that scenario, score it through the EXISTING pipeline exactly as typed
   text is scored. Full mockup already shown to and approved by the owner:
   see C:\Users\saika\AppData\Local\Temp\claude\c--Users-saika-sports-risk-nlp\
   87ca77e5-c2e0-495c-9a97-7e6d19d18495\scratchpad\matchday_synthetic_mockup.html
   (this is a temp scratchpad file, not in the repo -- re-read it for the
   exact CSS classes/visual shape before building the page, since it must
   look identical to this mockup, which the owner has already seen and liked).

3. Owner's newest ask (this is what's being planned/built): make the
   scenario picker richer --
     - more sports (mockup only had "Athletics -- 400m")
     - more competition stages, explicitly wanting "before/during/after the
       tournament"
     - more pressure-level / life-context scenarios: injury, breakup, good
       past season, etc. -- "several such scenarios"
     - CRITICALLY: the score must actually vary meaningfully by exact
       scenario selected, not just relabel the same generic passage.

4. Scope conflict found and RESOLVED (owner said "go with (b)"):
   synthetic.py's own docstring says post-match text was deliberately
   excluded from this project's scope (Phase 7 survey: "every athlete-speech
   corpus located is post-match, which is the wrong side of the event for
   this project" -- post-match constructs like relief/disappointment/
   attribution aren't in the taxonomy). So "during/after the tournament" as
   literal post-match text is OUT. Instead: offer TIMING variety strictly
   within the pre-competition window (e.g. "a month out" / "week before" /
   "morning of" / "immediately before call-time") plus LIFE-CONTEXT variety
   (injury_comeback / recent_loss / strong_season / personal_disruption /
   none) layered on top. This reads as "the different pressures of before,
   during a rough patch, after a setback" without ever generating text the
   taxonomy can't honestly score. State this explicitly to the owner again
   in whatever you build/report, since it's a real (resolved) scope call.

PART C -- THE PLAN (already presented to and approved by the owner)
===============================================================================

Phase 1 -- Scenario taxonomy (data only, no logic)
  Define a MatchDayScenario frozen dataclass: sport, timing (label mapped to
  a TIME_TO_COMPETITION_DAYS value or narrow range), life_context (none /
  injury_comeback / recent_loss / strong_season / personal_disruption --
  add more once CATEGORICAL_REALISATIONS is read, e.g. an
  "off-field disruption" bucket could map to perceived_stress + burnout).
  For each life_context, write an explicit, reviewable table: which
  constructs it biases toward and at what intensity band, grounded in
  AFFINITIES (don't invent unaffiliated combinations).

Phase 2 -- Scenario-aware generation
  Add generate_scenario_record(scenario, seed) -> RawRecord to synthetic.py
  (or a thin sibling module importing it) that replaces _draw_constructs's
  random draw with the Phase 1 bias table, then calls the EXISTING _realise/
  _fill/_vary machinery unchanged. Determinism test: same scenario + same
  seed -> identical record. Variation test: different life_context at fixed
  sport/timing -> measurably different construct set across N seeds
  (statistical, not single-sample).

Phase 3 -- Wire into the Match-Day page
  Expand dropdowns (sport / timing / life-context) per Phase 1's declared
  options. "Generate & score" button calls generate_scenario_record, then
  the existing build_view/LexiconBackend pipeline -- NO changes to scoring
  itself. Keep every stamp from the mockup (SYNTHETIC PASSAGE box, "not a
  real athlete" caption) exactly as shown in matchday_synthetic_mockup.html.
  dashboard/pages/6_Match_day_profile.py currently has NO photo/link upload
  at all (removed per an earlier explicit request this session) -- this
  phase replaces its current "paste a YouTube link" flow with the scenario
  picker instead. Read the CURRENT state of that file before editing --
  it may have been recommitted/changed since this handover was written.

Phase 4 -- Documentation
  PROJECT_PLAN.md: new phase entry (next number after Phase 29).
  docs/ethics.md: one-line note in the existing synthetic-data section
  pointing at the new bias table, so a reviewer can audit which constructs
  each scenario is designed to express.
  CLAUDE.md: phase record, matching the style of existing sections 12-14.

===============================================================================
