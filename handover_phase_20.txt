B1. THE ONE PLACE TWO PROJECT RULES CONTRADICTED EACH OTHER

The forbidden-vocabulary guard failed on its first run — against the mandated
provenance stamp. PROVISIONAL_STAMP reads "... corpus-property measurement, NOT
accuracy", so a flat substring ban on "accuracy" makes the required stamp
unshippable.

Resolved narrowly and deliberately: the literal denial "not accuracy" is allowed
and nothing else, matched literally rather than by detecting negation in general.
A cleverer rule would admit "no reason to doubt the accuracy", which is a claim
wearing a negation.
test_the_only_permitted_use_of_accuracy_is_the_stamps_own_denial pins four such
smuggling attempts. If a future surface needs another phrasing it adds a literal
and a test, deliberately, rather than the guard quietly widening.


B2. TWO DEFECTS FOUND BY LOOKING AT THE RENDERED PAGE, NOT BY ASSERTING

Both passed every unit test. Read this section — it is the phase's transferable
finding.

  B2.1 DUPLICATE SVG ELEMENT IDS. Both charts defined the pattern id
       "inert-hatch". SVG ids share ONE NAMESPACE PER DOCUMENT, and Streamlit
       keeps the DOM of every tab mounted, so the second chart's definition won
       the reference and the first chart's hatch rendered as an empty box — the
       exact marking that C2.5 requires. The unit tests render each chart in
       isolation and stayed green throughout. Fixed: pattern ids are now derived
       deterministically from the chart's own data (hash of construct,
       contribution, probability, inert), so they are unique per chart and stable
       across runs. Pinned by test_two_charts_on_one_page_do_not_share_a_pattern_id.

  B2.2 A PROVENANCE STAMP INSIDE A COLLAPSED EXPANDER. The PROVISIONAL stamp was
       rendered only inside st.expander(...), which Streamlit renders collapsed.
       Present in the DOM; absent from the screen, and absent from every
       screenshot that becomes a paper figure. A DOM-level test would have passed
       forever. Fixed: the stamp is rendered above the risk meter, and
       test_the_stamp_is_rendered_outside_any_collapsed_container asserts it
       appears before the first st.expander call.

  B2.3 A THIRD, IN THE FIGURE SCRIPT: composing the paper figure by slicing the
       child SVGs' markup into <g> wrappers produced a blank figure — each
       child's own </svg> closed the parent early. Caught because the script
       writes a proof image and someone looked at it. Now composed as nested
       <svg> elements with x/y offsets.

  COMMON SHAPE, and it is the same one as Phases 9b/17/18: the check and the
  thing it protects were related by assumption. What is new is WHERE it hid — one
  level below the tests, in the composition of independently-correct parts. The
  tests were not wrong; they were scoped to a single chart, and the defect only
  exists when two charts share a document.


B3. DECISIONS TAKEN THIS SESSION (owner-confirmed at the start)

  1. LIVE SCORING USES THE LEXICON BASELINE, NOT THE TRANSFORMER. The dashboard
     compose service runs the LIGHT image, which has no torch by design (Phase 2).
     Loading the checkpoint would mean the multi-GB train image, a slow cold
     start, and a Docker gate that no longer runs in the image the rest of the
     project uses. C2.7 also binds: the paper's model must not silently change,
     and the surest guarantee is that the demo does not hold it. A
     TransformerBackend satisfying the same Protocol is a contained addition if a
     live demo is ever needed.

     CONSEQUENCE THE PAPER MUST CARRY: the live tab shows the 0.462 floor, not
     the 0.588 model, and it is not corpus-independent (OPEN-021). The app states
     this on screen every time. Do not screenshot the live tab as though it were
     the system's output.

  2. THE LEXICON EMITS PRESENCE, NOT PROBABILITY, AND THAT IS LEFT VISIBLE.
     LexiconBaseline.predict returns a set of matched constructs; it has no
     probability to give. Rather than invent one from cue-hit counts — an
     arbitrary formula that would look exactly like a model score on a bar chart
     — the live path reports 1.0/0.0 and the view labels the axis accordingly.
     The bars look blocky. A made-up magnitude on a screening tool is the kind of
     number that gets quoted back without its formula.

  3. THE KNOWN-EXAMPLE FIXTURE IS DERIVED FROM reports/explain/cards.md, frozen
     into tests/fixtures/dashboard_known_examples.json, and the gate compares the
     dashboard's rendering of the FIXTURE against the committed cards.md. The
     reports are regenerated whenever run_explain.py runs; a gate that moves with
     its own subject is not a gate.

     How the probabilities were recovered exactly: cards.md prints p to 2dp
     (too coarse) but contribution to 3dp, and contribution = probability *
     weight with the weight fixed by DEFAULT_MAGNITUDES. Division recovers p at
     3dp. Polarity-bearing constructs never appear in the drivers table
     (contribution is exactly zero), so theirs come from attributions.json.
     scripts/build_dashboard_fixture.py VERIFIES the reconstruction by
     re-rendering and REFUSES to write a fixture that does not reproduce cards.md
     byte for byte. It reproduced on the first attempt.


B4. CHART FORM — BOTH OBVIOUS DEFAULTS WERE WRONG, AND THE REASONS GENERALISE

  A RADIAL GAUGE IS THE WRONG MARK FOR THE RISK INDEX. A dial's arc reads as a
  proportion of a whole; the index is an uncalibrated ranking score. The
  speedometer form also carries a strong "measurement of a thing" connotation,
  which for a number explicitly NOT a measurement of a person is the connotation
  to avoid. Replaced with a LINEAR METER — a position, not a verdict. The track
  carries NO low/moderate/high bands: banding an uncalibrated score invents
  thresholds nothing in this project supports, and a coloured band is read as a
  judgement about a person.

  A TEN-HUE CATEGORICAL CHART IS THE WRONG MARK FOR THE DECOMPOSITION. Ten
  categorical hues are indistinguishable to everyone. The constructs are rows of
  one comparison, not series, so the encoding is position down a shared axis — a
  DIVERGING BAR CHART, left of the rule lowers risk, right raises it.

  SIGN IS ENCODED BY POSITION, NOT COLOUR, so it survives grayscale, print, any
  colour vision, and a stripped stylesheet. Colour is a redundant second channel.

  THE FOUR INERT CONSTRUCTS ARE MARKED THREE TIMES OVER: hatch fill, dashed
  outline, and the literal word "inert" in the row label. Verified against Phase
  24's "figures legible in grayscale" gate by a desaturated proof image, which is
  committed. A colour-only marking passes review on a screen and fails in print,
  after the figure has been drawn.

C4. THE DEFECT TO EXPECT IN PHASE 21 — PREDICTED IN ADVANCE

  Four phases in a row have now found the same shape. Phase 21's version is
  easy to name because a security phase is made almost entirely of gates:

      A SCANNER REPORTING "0 FINDINGS" WILL BE ACCEPTED AS "THERE IS NOTHING TO
      FIND", WITHOUT ANYONE CHECKING WHAT THE SCANNER ACTUALLY LOOKED AT.

  Concretely, the things to verify BEFORE trusting a clean report:
    - detect-secrets already has a .secrets.baseline in this repo (4,035 bytes).
      A baseline is a list of findings someone decided to ignore. Read it. A
      clean scan against a stale baseline is a laundered claim, exactly OPEN-034.
    - .env EXISTS in the working tree (92 bytes) and .gitignore is 4,689 bytes.
      Confirm .env has never been committed by checking HISTORY, not the index:
      `git log --all --full-history -- .env` must return nothing.
    - donations_inbox.jsonl (522 bytes) sits at the repo ROOT and is not in any
      data/ directory. Phase 21's PII sweep must cover it explicitly; a sweep
      scoped to data/ would miss it entirely. Check whether it is tracked.
    - The dependency scan must cover requirements-base.txt, requirements-ml.txt
      AND requirements.lock.txt. Scanning only the first reports on the light
      image and says nothing about the training image.
    - Write down what each tool DOES NOT cover, in docs/security.md, next to what
      it found. That sentence is what stops the next reader from over-reading a
      clean result.

  The fix in every previous instance was the same: make the relationship between
  the check and the property explicit and machine-checkable.
