B1. A REPOSITORY-INTEGRITY DEFECT FOUND AND FIXED — READ THIS

Phase 17 AND Phase 18 were both uncommitted. git HEAD was still
"d18405a feat(phase14)" while src/explainability/, src/evaluation/{harness,
ablations}.py, scripts/run_{explain,evaluation}.py, both test modules, all of
reports/explain/ and all of reports/results.* existed only on the owner's disk.
Two phases of work with no off-machine backup, in a project whose own
PROJECT_PLAN.md says "push at the end of every phase; a remote that stops
receiving pushes is not a backup."

Root cause: a stale .git/index.lock aborted the Phase 18 commit, the failure was
read as success, and the Phase 17 commit had never been made at all.

CARRY FORWARD: after every phase, verify the commit LANDED — `git log --oneline
-1` must show it — rather than trusting that the command was issued. This is the
same defect shape as OPEN-034: the check ("I ran git commit") and the thing it
protects ("the work is backed up") were related by assumption, not by
construction.

Secondary finding, environment-level: when a Cowork session reaches the repo
through the desktop folder bridge, git cannot unlink its own lock files
("Operation not permitted"), so `git add` succeeds and `git commit` fails.
Git operations in this repo must be run by the owner in PowerShell, or the
Cowork task must be started on the owner's computer rather than in the cloud.
